풋살 대회 기록 웹 계획서
2026년 10월 6일 · @박진
개요
풋살 대회 당일, 운영진이 경기 결과를 실시간으로 입력하면 조별 순위와 결승·3·4위전 대진이 자동으로 계산되고, 누구나 결과 페이지에서 볼 수 있는 웹을 만든다. 중등부와 고등부는 완전히 따로 운영하고, 대회는 하루(4개 구장 동시 진행)에 끝난다.

대회 규칙
두 부문 모두 3팀씩 2개 조(A조: 1~3번, B조: 4~6번)로 조별 풀리그를 한 뒤, 조 1위끼리 결승, 조 2위끼리 3·4위전을 한다.
• 팀 배정: 학교와 번호(조)는 대회 당일 추첨으로 정한다.
• 팀 수: 고등부 6팀 확정. 중등부는 4~6팀 중 미정이며, 코드 수정 없이 대응할 수 있어야 한다.
• 승점: 승 3, 무 1, 패 0. 조별 리그는 무승부를 허용한다.
• 매너점수: 경고 −1, 퇴장 −3. 0에서 시작해 감점하며 높을수록 좋다.
• 순위 기준(조 안에서만 비교): 매너점수 → 승점 → 득실차 → 다득점 → 승자승. 이 순서는 대회 요강대로 매너점수가 1순위다.
• 출장정지: 퇴장 받은 선수는 그 팀의 다음 경기에 출장할 수 없다. 경고 누적으로는 출장정지되지 않는다.
• 토너먼트 동점 처리: 미정(연장 후 승부차기, 또는 바로 승부차기).

핵심 설계: 번호 슬롯과 진출 규칙
팀 수와 조 편성이 바뀌어도 코드를 고치지 않도록, 경기는 "번호(슬롯)"끼리, 토너먼트는 "진출 규칙"으로 저장한다.
번호 슬롯
• 경기는 처음부터 고등1 vs 고등2처럼 슬롯끼리 잡아 seed한다.
• 당일 추첨 후 운영진이 슬롯에 학교를 배정한다(예: 중등3 = ○○중).
• 화면은 배정 전에는 번호, 배정 후에는 학교명을 보여준다.
• 중등부 팀 수가 바뀌면 슬롯과 경기 목록 데이터만 바꾼다(예: 5팀이면 B조 슬롯 4·5만 사용).
진출 규칙
• 결승과 3·4위전은 팀 대신 출처를 저장한다: A:1(A조 1위), B:2(B조 2위) 같은 형식.
• 해당 조의 경기가 모두 종료되면 순위를 계산해 실제 팀으로 채운다.
• 단일 리그로 바뀌면 L:1 vs L:2처럼 규칙만 바꾸면 된다.
• 계산이 애매한 경우(모든 기준 완전 동률 등)를 위해 운영진이 팀을 직접 지정하는 수동 오버라이드를 둔다.
데이터 모델
Supabase 테이블 5개로 구성하고, 순위표는 저장하지 않고 matches와 cards에서 매번 계산한다. 그래야 결과를 수정해도 순위가 어긋나지 않는다.

매너점수·출장정지 계산 근거
• 연장(*_et)과 승부차기(*_pk)는 nullable로 두어, 동점 처리 방식이 어떻게 정해져도 저장할 수 있게 한다.
• 이벤트 경기는 기록 여부가 정해지면 stage에 event를 추가한다.
순위 계산 로직
순위 계산은 DB와 분리된 순수 함수(lib/standings.ts)로 만들고, UI보다 먼저 테스트를 작성한다.
1. 입력: 한 조의 슬롯 목록, status = finished인 조별 경기, 해당 경기의 카드 목록.
2. 팀별로 경기수, 승·무·패, 득점, 실점, 득실차, 승점, 경고 수, 퇴장 수, 매너점수를 집계한다.
3. 정렬 기준 배열 RANKING_ORDER = ['manner', 'points', 'goalDiff', 'goalsFor', 'headToHead']를 설정값으로 두고 순서대로 비교한다.
4. 승자승은 동률인 팀끼리의 경기만으로 승점을 다시 계산해 비교한다(3팀 동률도 처리).
5. 모든 기준이 같으면 동률로 표시하고, 운영진 수동 지정을 요구한다.
진출 규칙 해석: A:1은 A조의 모든 경기가 finished일 때만 팀으로 바뀌고, 그 전에는 "A조 1위"로 표시한다. manual 값이 있으면 그것을 우선한다.
출장정지: 선수에게 red 카드가 있으면, 그 팀의 다음 경기(start_time 기준)에서 출장정지로 표시한다.
테스트 케이스(최소): 매너점수가 승점을 뒤집는 경우, 득실차 동률 후 다득점, 2팀 승자승, 3팀 완전 동률, 2팀짜리 조, 경기 일부만 종료된 상태.
화면 구성
공개 페이지 1개와 비밀 주소의 운영진 페이지 3개로 구성한다. 대회 당일 경기장 옆에서 폰으로 보고 입력하므로 모바일 우선으로 만든다.

보안 방침
로그인 없이 비밀 주소로 운영진 페이지를 보호하기로 했다(유출 위험은 감수). 대신 DB를 브라우저에서 직접 수정할 수 없게 막는다.
• 비밀 경로는 환경변수(ADMIN_PATH)로 관리하고 코드·저장소에 하드코딩하지 않는다.
• Supabase RLS: anon 키는 모든 테이블 읽기만 허용한다.
• 모든 쓰기는 Next.js 서버 액션에서 service role 키(SUPABASE_SERVICE_ROLE_KEY, 서버 전용)로만 수행한다.
• 운영진 페이지에 noindex를 넣어 검색 노출을 막는다.
구현 순서
각 단계는 끝날 때마다 동작을 확인하고 커밋한 뒤 다음 단계로 넘어간다.
1. DB 준비: Supabase 테이블 5개, RLS(읽기 전용), 시간표 seed 스크립트, 참가 신청 시트(xlsx) → teams·players import 스크립트.
2. 순위 로직: lib/standings.ts와 진출 규칙 해석, 출장정지 판정. 테스트 케이스 먼저 통과시킨다.
3. 공개 페이지: 부문 탭, 시간표 그리드, 조별 순위표, 토너먼트 카드.
4. 운영진 페이지: 추첨 배정 → 경기 입력 → 토너먼트 확정, 서버 액션으로 쓰기.
5. 실시간·배포: Supabase Realtime 구독, Vercel 배포, 환경변수 설정.
6. 리허설: 가짜 팀·결과로 대회 하루(추첨부터 시상까지)를 처음부터 끝까지 돌려보고, 폰으로 입력 속도를 확인한다.
